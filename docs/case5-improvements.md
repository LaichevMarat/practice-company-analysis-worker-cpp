## Сводная таблица

| № | Проблема | Причина | Способ решения | Ожидаемый эффект |
|---|---|---|---|---|
| 1 | Стаж считается по годам, а не по датам | В классе хранится только `hireYear` | Хранить полную дату приёма (`std::chrono::year_month_day`), вычислять стаж в днях и переводить в полные годы | Точность стажа до дня; корректная работа на границе года и при годовой отчётности |
| 2 | Денежные расчёты в `double` | Оклад хранится как `double` | Хранить сумму в копейках (`std::int64_t`) либо использовать десятичный тип; форматировать при выводе | Исключение ошибок округления при суммировании и индексации окладов |
| 3 | Данные не сохраняются между запусками | Нет слоя хранения | Сериализация в CSV/JSON или таблица в SQLite; интерфейс `IWorkerRepository` | Возможность вести учёт постоянно, а не вводить список заново |
| 4 | Нет истории изменений окладов и должностей | Сеттеры перезаписывают значение | Журнал изменений: запись «кто, когда, что, старое → новое» (паттерн Memento/аудит) | Прозрачность кадровых решений, возможность разбора спорных ситуаций |
| 5 | Нет учёта увольнений и переводов | Модель описывает только текущее состояние | Добавить `dismissalDate` и `status`; отбор по стажу — только для действующих сотрудников | Корректные отчёты по штату, а не по всем, кто когда-либо работал |
| 6 | Разбор файла и аргументов не покрыт тестами | Тесты писались для класса, а не для ввода | Вынести разбор в отдельные функции и покрыть тестами: пустой файл, BOM, лишние `;`, неверный год, отрицательный оклад | Регрессии в загрузке данных ловятся автоматически |
| 7 | Фильтрация полным перебором `std::list` | Линейный поиск по связному списку | `std::vector` + сортировка по стажу и бинарный поиск; для больших объёмов — индекс в БД | Снижение сложности с O(n) до O(log n) на запрос |
| 8 | Повторяющиеся сотрудники попадают в список дважды | Нет проверки уникальности | Ключ уникальности (ФИО + год поступления), `std::set` или проверка при добавлении | Чистота данных, отсутствие двойного учёта |
| 9 | Валюта и формат чисел зашиты в код | «руб.» и разделитель в `toString` | Вынести локаль и валюту в настройки/`std::locale` | Возможность работы с другими валютами и форматами |
| 10 | Ошибка ввода при EOF аварийно завершает программу | `std::getline` при неудаче бросает исключение | Возврат к меню вместо завершения; отдельный код возврата | Устойчивость при работе с перенаправленным вводом и в пакетных сценариях |
| 11 | Нет экспорта отчёта | Вывод только на экран | Экспорт выборки в CSV и формирование текстового отчёта | Результат можно приложить к отчётной документации |
| 12 | Нет автоматической сборки и проверки | Тесты запускаются вручную | GitHub Actions: сборка g++ и прогон `worker_tests` на каждый push | Ошибки находятся до сдачи, а не после |

## Приоритизация

Все проблемы разделены на три очереди по соотношению «польза / трудозатраты».

**Первая очередь (обязательно, дешёво):**

- № 6 — тесты на разбор файла: закрывает самый вероятный источник регрессий;
- № 4 — история изменений: без неё учёт окладов теряет смысл;
- № 12 — CI: одна конфигурация, экономит время на каждой итерации.

**Вторая очередь (существенно для реальной эксплуатации):**

- № 1 — точная дата приёма;
- № 2 — денежный тип;
- № 3 — сохранение данных;
- № 5 — увольнения и переводы.

**Третья очередь (по мере роста объёма данных):**

- № 7 — индексы и сортировка;
- № 8 — уникальность;
- № 9 — локализация;
- № 11 — экспорт отчётов;
- № 10 — устойчивость интерактивного режима.

## Ключевые решения с примерами

### 1. Точный стаж по дате приёма

Проблема: `experience(2026) - hireYear` даёт до 12 месяцев погрешности.

```cpp
#include <chrono>

std::chrono::year_month_day hireDate_;  // вместо int hireYear_

int Worker::experience(const std::chrono::year_month_day& on) const noexcept {
    using namespace std::chrono;
    const auto years = (on.year() - hireDate_.year()) -
                       (on.month() < hireDate_.month() ? 1 : 0);
    return years.count() < 0 ? 0 : static_cast<int>(years.count());
}
```

Заодно снимается ограничение «год не больше текущего»: проверяется корректность
даты, а не диапазон года.

### 2. Деньги в минорных единицах

Проблема: `0.1 + 0.2 != 0.3` в двоичной плавающей точке.

```cpp
std::int64_t salaryKopecks_;  // 120000.00 руб. -> 12000000 копеек

std::string Worker::salaryText() const {
    return std::to_string(salaryKopecks_ / 100) + "," +
           (salaryKopecks_ % 100 < 10 ? "0" : "") +
           std::to_string(salaryKopecks_ % 100);
}
```

Суммирование и индексация становятся точными; округление выполняется один раз —
при выводе.

### 3. Отбор без полного перебора

Проблема: `std::list` не даёт произвольного доступа, каждый запрос — O(n).

```cpp
// Список поддерживается отсортированным по году приёма (по возрастанию стажа).
// Тогда сотрудники со стажем больше N — это префикс диапазона, и поиск
// выполняется за O(log n) через std::lower_bound.
auto first = std::lower_bound(workers.begin(), workers.end(), thresholdYear,
                              [](const Worker& w, int year) {
                                  return w.hireYear() > year;
                              });
```

Для объёмов свыше ~100 тыс. записей разумнее перенести выборку в СУБД с индексом
по `hire_year`.

### 4. Журнал изменений

Проблема: после `setSalary` прежнее значение безвозвратно теряется.

```cpp
struct SalaryChange {
    std::string workerName;
    std::chrono::system_clock::time_point moment;
    double oldValue;
    double newValue;
    std::string reason;
};
```

Журнал хранится отдельно от объекта: сам `WORKER` остаётся простой моделью, а
аудит — сквозная функциональность, которая не должна засорять предметный класс.

### 5. Тесты на разбор файла

Проблема: ошибка в парсере обнаружится только при ручном запуске.

```cpp
TF_TEST("loadFromFile отклоняет строку без года") {
    TF_CHECK_THROW(loadFromFile("tests/data/bad_year.txt"), std::runtime_error);
}
```

Проверяются: пустой файл, файл только с комментариями, BOM, лишние `;`, оклад
с запятой вместо точки, год из будущего.

## План внедрения

1. **Неделя 1.** Тесты на разбор файла, CI-конфигурация, рефакторинг парсера в
   отдельный модуль `src/parser.cpp`.
2. **Неделя 2.** Переход на точную дату приёма и денежный тип; миграция данных
   `workers_demo.txt`.
3. **Неделя 3.** Слой хранения: `IWorkerRepository`, реализация CSV/SQLite,
   сохранение между запусками.
4. **Неделя 4.** История изменений и статусы (работает/уволен), отчёты и экспорт.

Каждый шаг завершается прогоном всех тестов и коммитом — так регрессии видны
сразу, а не накапливаются к концу практики.

## Вывод

Решение кейс-задачи № 3 работоспособно и покрыто тестами, но ориентировано на
учебный сценарий: небольшие объёмы, один запуск, отсутствие истории. Выявленные
проблемы не являются ошибками реализации — это границы выбранной модели, и они
превращены в конкретный план работ с приоритетами. Первоочередные меры (тесты
парсера, журнал изменений, CI) дают наибольший эффект при минимальных затратах,
а переход к точным датам и денежному типу устраняет принципиальные ограничения
предметной области.
