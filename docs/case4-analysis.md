## 1. Атрибуты (свойства)

Данные, которые хранит каждый объект класса `WORKER`, и обоснование выбора типов:

| Атрибут | Поле | Тип | Обоснование |
|---|---|---|---|
| Фамилия и инициалы | `fullName_` | `std::string` | Строка произвольной длины, допускает кириллицу и дефисы («Петрова-Водкина А.С.»); стандартный тип не требует ручного управления памятью |
| Должность | `position_` | `std::string` | Значение приходит из штатного расписания организации, набор не фиксирован — перечисление (`enum`) сделало бы класс негибким |
| Зарплата | `salary_` | `double` | Оклад задаётся в рублях и допускает копейки; для учебной задачи точности `double` достаточно (в разделе 12 отмечено, почему в промышленном коде нужен десятичный тип) |
| Год поступления на работу | `hireYear_` | `int` | Требование задания — именно год, а не дата; целое число удобно для расчёта стажа и валидации диапазона |

Инварианты объекта, которые обязаны выполняться всегда:

1. `fullName_` и `position_` не пусты (после удаления пробелов по краям);
2. `salary_ >= 0` и является конечным числом (не `NaN`, не бесконечность);
3. `1900 <= hireYear_ <= текущий год`.

## 2. Методы (функции)

| Группа | Метод | Назначение |
|---|---|---|
| Конструирование | `Worker()` | Конструктор по умолчанию: «пустой» сотрудник со стажем 0 |
| | `Worker(fullName, position, salary, hireYear)` | Основной конструктор с параметрами и валидацией |
| | `Worker(fullName, position)` | Дополнительный конструктор: год поступления = текущий |
| | `Worker(const Worker&)`, `operator=` | Копирование и присваивание |
| | `~Worker()` | Деструктор |
| Доступ | `fullName()`, `position()`, `salary()`, `hireYear()` | Геттеры, `const noexcept`, возвращают ссылку/значение без копирования строки |
| Изменение | `setFullName`, `setPosition`, `setSalary`, `setHireYear` | Поштучное изменение с проверкой значения |
| | `edit(name, position, salary, year)` | Атомарное изменение всех полей |
| | `raiseSalary(percent)` | Повышение оклада на процент (индексация) |
| Согласно заданию | `experience(currentYear)` | Стаж в полных годах на заданный год |
| | `experienceExceeds(years, currentYear)` | Проверка «стаж строго больше порога» |
| | `selectByMinExperience(list, years, year)` | Отбор сотрудников из списка по стажу |
| Отображение | `toString()`, `toString(year)`, `print(os)`, `operator<<` | Текстовое представление для экрана и для тестов |

Разделение «изменение по одному полю» и «изменение всех полей» сделано осознанно:
сеттеры удобны для точечных правок, а `edit` даёт гарантию, что объект не останется
в промежуточном состоянии, если одно из значений окажется некорректным.

## 3. Абстракция

Абстракция — это выделение существенного для задачи и отбрасывание несущественного.
В модели оставлены только те характеристики работника, которые нужны для решения
задачи: кто он (`fullName_`), кем работает (`position_`), сколько получает
(`salary_`) и когда пришёл (`hireYear_`).

Сознательно **не** включены: паспортные данные, адрес, телефон, ИНН, семейное
положение, табельный номер. Они не участвуют ни в одном методе задания, а их
хранение увеличило бы класс и создало бы риск утечки персональных данных.

Поведение объекта тоже абстрагировано: внешний код не знает, как именно считается
стаж, — он вызывает `experience()` и получает результат. Если завтра потребуется
считать стаж по точной дате приёма, изменится только реализация метода, а не
клиентский код.

## 4. Инкапсуляция

Все четыре поля объявлены в секции `private`. Прямой доступ извне невозможен,
изменение — только через методы, которые проверяют инварианты:

```cpp
void Worker::setSalary(double salary) {
    requireNonNegativeSalary(salary);   // проверка до изменения
    salary_ = salary;
}
```

Что это даёт:

- **Сохранение инвариантов.** Отрицательный оклад или год из будущего не могут
  попасть в объект ни через конструктор, ни через сеттер, ни через `edit`.
- **Атомарность изменения.** `edit` сначала проверяет все четыре значения и только
  потом присваивает — объект не остаётся «полуизменённым».
- **Свобода эволюции.** Внутреннее представление можно поменять (например,
  хранить полную дату приёма вместо года), не затрагивая вызывающий код.
- **Читаемость.** `worker.experience(2026)` говорит само за себя, тогда как
  `2026 - worker.hireYear` размазывает логику по вызывающему коду.

Поля-геттеры возвращают `const std::string&`, чтобы не копировать строку на каждом
обращении, но при этом не дают возможности изменить поле в обход сеттеров.

## 5. Наследование

На текущем этапе наследование **не используется**, и это осознанное решение:
в задании есть ровно один тип сущности, а введение базового класса `Person` ради
одного наследника только усложнило бы код (правило «не вводить абстракцию без
второго потребителя»).

Наследование станет оправданным, когда появятся разные категории сотрудников:

```
Person (ФИО, дата рождения)
   └── Employee (должность, оклад, год поступления)
          ├── Teacher   (учёная степень, учебная нагрузка)
          └── Engineer  (стек технологий, грейд)
```

Тогда общие поля (`fullName`, `hireYear`) поднимаются в `Person`, а расчёт
выплат и стажа остаётся в `Employee`. Класс `WORKER` в текущем виде можно
рассматривать как готового кандидата в `Employee`.

## 6. Полиморфизм

Подклассов сейчас нет, поэтому и полиморфизма нет — ни виртуальных функций, ни
абстрактных методов. Это соответствует принципу YAGNI: виртуальный деструктор
и `virtual double calculateSalary()` при одном классе дали бы только накладные
расходы (таблица виртуальных функций, невозможность инлайна).

Точки, где полиморфизм понадобится:

- **Расчёт выплат.** У преподавателя — оклад + надбавка за нагрузку, у инженера —
  оклад + премия за проект. Реализуется виртуальным `calculateSalary()`.
- **Отображение.** Разные наборы полей в отчёте — виртуальный `toString()`.
- **Отбор.** Разные критерии (по стажу, по грейду) — интерфейс `IWorkerFilter`
  со стратегиями.

Важно, что текущий интерфейс класса (`experience`, `experienceExceeds`) уже
сформулирован в терминах поведения, а не полей, поэтому добавление наследников
не потребует менять вызывающий код.

## 8. Тестирование

Разработан набор из **25 модульных тестов** (`tests/test_worker.cpp`), который
запускается командой `build\worker_tests.exe` и не требует внешних библиотек.

Покрытие по группам:

| Группа | Кол-во | Что проверяется |
|---|---|---|
| Конструкторы | 7 | Значения по умолчанию, параметризованный конструктор, обрезка пробелов, отказ при пустых ФИО/должности, отрицательном окладе, некорректном годе |
| Копирование | 2 | Независимость копии, полнота копирования полей |
| Методы изменения | 5 | Работа сеттеров, сохранение значения при ошибке, атомарность `edit`, индексация оклада |
| Стаж | 3 | Расчёт стажа, отсутствие отрицательного стажа, строгость неравенства на границе |
| Отображение | 3 | Наличие всех полей в строке, склонение слова «год», согласованность `operator<<` и `print` |
| Отбор по стажу | 4 | Фильтрация, сохранение порядка, пустой результат, пустой список |

Результат прогона:

```
Всего тестов: 25, успешно: 25, провалено: 0
```

Приёмы тестирования:

- **Граничные значения.** Стаж ровно равен порогу — сотрудник не попадает в выборку
  (`experienceExceeds` использует строгое `>`); год поступления 1800 и «текущий + 1»
  отклоняются.
- **Негативные сценарии.** Проверяется, что исключение действительно выбрасывается
  (`TF_CHECK_THROW`) и что объект при этом не изменился.
- **Свойства, а не реализация.** Тесты не зависят от формата вывода целиком —
  проверяется наличие значимых фрагментов, поэтому косметические правки не ломают
  тесты.

Чего тесты пока не покрывают: разбор файла (`loadFromFile`) и разбор аргументов
командной строки — эти пункты вынесены в план улучшений (кейс-задача № 5, п. 6).

## 10. Итерация

После первого рабочего варианта код был пересмотрен, и в него внесены изменения:

| Что было | Что стало | Причина |
|---|---|---|
| `edit` присваивал поля по одному | Проверка всех значений, затем присваивание | Исключение на третьем поле оставляло объект изменённым наполовину |
| Стаж мог стать отрицательным при годе из будущего | `experience` возвращает 0 | Защита от некорректных данных |
| Слово «лет» во всех случаях | Склонение «год/года/лет» | Читаемость отчёта |
| Поиск подходящих сотрудников внутри `main` | Отдельная функция `selectByMinExperience` | Логику стало возможно протестировать отдельно от ввода-вывода |
| Сравнение стажа `>=` | Строгое `>` | Требование задания: «превышает значение» |
| Нет проверки ввода | Повторный запрос при некорректном вводе | Программа не падает на опечатке |
| Файл с BOM не читался | BOM обрабатывается | Файлы, сохранённые в Блокноте, открываются корректно |

Дальнейшая итерация описана в `docs/case5-improvements.md`.

## 11. Ограничения текущего решения

Честно перечисленные слабые места (они же — исходные данные для кейс-задачи № 5):

1. Стаж считается по календарным годам, а не по точной дате приёма, — на границе
   года возможна погрешность до 12 месяцев.
2. Оклад хранится в `double`, что для денежных расчётов даёт риск накопления
   ошибки округления.
3. Данные живут только в памяти процесса: нет сохранения между запусками.
4. Нет истории изменений — кто и когда менял оклад, не фиксируется.
5. Фильтрация выполняется полным перебором `std::list` — для десятков тысяч
   записей это медленно.
6. Разбор файла и аргументов командной строки не покрыт тестами.
7. Нет сборки CI: тесты запускаются вручную.

## 12. Вывод

Класс `WORKER` реализован в отдельном модуле, инкапсулирует четыре поля, проверяет
инварианты при любом изменении и предоставляет методы как для точечного, так и для
атомарного изменения. Логика отбора по стажу вынесена в отдельную функцию и покрыта
тестами вместе с остальным поведением класса (25 тестов). Наследование и
полиморфизм сознательно не введены — для одной сущности они не дают выигрыша, но
точки их будущего применения определены. Ограничения решения зафиксированы явно и
превращены в план работ (кейс-задача № 5).
